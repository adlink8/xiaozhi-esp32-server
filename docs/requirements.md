## 1. 项目概述

- **项目名称**：小智后端服务 xiaozhi-esp32-server
- **项目类型**：面向 ESP32 智能硬件（"小智"智能音箱等）的本地/自部署 AI 后端服务
- **核心能力**：
  - 语音对话（ASR + LLM + TTS）
  - 视觉感知（VLLM、多模态能力）
  - 设备控制（MQTT+UDP、WebSocket、MCP 工具调用、指令下发）
  - 记忆与知识库（短期记忆、mem0ai、PowerMem、RAGFlow）
  - 管理端（manager-api + manager-web + manager-mobile）

> 建议你在这里用 3~5 句话描述“你在自己环境里想达到的效果”，比如：
> - 面向家庭场景的个人智能助手
> - 面向某个垂直业务（如医疗、教育、企业陪练）的专用终端

## 2. 项目范围（Scope）

### 2.1 当前计划覆盖范围

- **设备侧**：
  - 支持指定型号 ESP32 设备接入（详见 CLAUDE.md 中的硬件配置）
  - 支持通过 MQTT+UDP 和 WebSocket 进行音频与指令双向通信

- **AI 服务侧**：
  - 支持至少一种可用的 ASR 服务（本地 FunASR 或云端）
  - 支持至少一种可用的 LLM 服务（如 qwen-flash 或 glm-4-flash）
  - 支持至少一种可用的 TTS 服务（本地或云端）
  - 支持至少一种记忆方式（本地短期记忆 / mem0ai / PowerMem）

- **管理端**：
  - Web 智控台（manager-web）可查看设备状态、基础配置
  - Java 后端（manager-api）提供配置、用户和设备管理接口
  - 移动端（manager-mobile）提供基本控制能力（目标视你是否打算启用）

- **部署与运维**：
  - 支持 Docker 全模块部署和源码模式部署
  - 支持在局域网环境内稳定运行

### 2.2 明确排除范围（可按需调整）

- 不保证公网暴露环境下的安全性与高可用性（README 中已有警告）
- 不承诺支持所有云厂商的全部型号与计费模式
- 非目标：大规模多租户 SaaS 平台

> 如果你有更明确的“暂不考虑”的范围，例如“暂不支持多租户账号体系”、“暂不支持多设备分组策略”，可以写在这里，避免需求不断膨胀。

## 3. 功能需求

### 3.1 核心功能模块

> 以下根据 README.md 的功能清单整理成“需求视角”，请按实际需要标记优先级。

1. **语音交互**
   - 支持终端设备通过麦克风录音并推送音频流至后端
   - 后端使用配置好的 ASR 服务进行实时或准实时语音识别
   - LLM 根据用户意图生成自然语言回复
   - TTS 将回复转换为语音并推送回终端播放

2. **设备接入与管理**
   - 支持 MQTT+UDP 网关接入多个 ESP32 设备
   - 支持设备在线状态的查看与基本信息展示
   - 支持通过管理端触发指令下发至设备（如播放、控制家电、执行插件任务）

3. **智能对话与插件调用**
   - 支持多种 LLM 接入（openai 风格接口 + 各种平台适配）
   - 支持函数调用 / MCP 工具调用，用于执行具体任务（如 HomeAssistant、天气、RAG 等）

4. **记忆与知识库**
   - 支持本地短期记忆，用于最近会话上下文维护
   - 可选接入 PowerMem / mem0ai / RAGFlow 等，用于长期记忆与知识库检索

5. **管理后台**
   - 登录与基础权限控制（若你有明确需求，可在这里细化）
   - 用户管理（查看、禁用、配置策略等）
   - 设备管理（查看设备列表、状态、绑定关系）
   - 配置管理（AI 服务密钥、模型选择、部署模式等）

### 3.2 可选 / 扩展功能

- 视觉感知（图像识别、拍照识物）
- 多模态对话（图文混合输入、语音+视觉）
- 高级插件系统（更多第三方服务、更多 IoT 协议）

> 建议：在每条功能旁边，后续用标签标记：`[Must]` / `[Should]` / `[Could]`。

## 4. 非功能性需求

> 当前仓库没有系统性的 NFR 文档，下面是一个起点。

1. **性能**
   - 在单用户交互场景下，对话往返响应时间应在可接受范围（例如 3–5 秒内，视模型与网络而定）
   - 默认并发连接数可覆盖你环境中预计的设备数量（例如 1–6 台设备）

2. **稳定性与可用性**
   - 后端服务在长时间运行下不会因单次错误崩溃
   - 支持通过日志与简单运维手段定位常见问题

3. **安全性**
   - API 密钥与敏感配置不写死在代码中，统一从配置文件或环境变量注入
   - 用于公网暴露时，明确阅读 README 中安全警告并按需加上反向代理 / 防火墙 / 认证等

4. **可维护性**
   - 关键模块遵循已有的代码规范（CLAUDE.md 中指出的 Python/Java/TS 规范）
   - 新增功能应配备最基础的文档（在 docs/ 中补充对应说明）

## 5. 优先级与阶段划分（草案）

> 以下只是示例，请根据你自己的规划调整。

- **阶段 1：本地单机智能音箱**
  - Must：单设备语音对话链路打通（ASR → LLM → TTS）
  - Must：基础配置文件（config.yaml 等）在本地环境正确运行
  - Should：简单的 Web 管理页面可以查看服务状态

- **阶段 2：多设备 + 管理端完善**
  - Must：支持多设备接入与基本管理
  - Should：管理端里可以配置不同的模型组合（免费/流式等）
  - Could：移动端管理界面可用

- **阶段 3：知识库与插件扩展**
  - Should：接入 RAGFlow / PowerMem 等知识库或记忆组件
  - Could：更多第三方工具集成（HomeAssistant、天气、短信等）
